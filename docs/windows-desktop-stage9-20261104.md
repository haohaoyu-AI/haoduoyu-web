## 核实的正式契约

正常无登录复核公开静态 OpenAPI（836155 B，SHA256 `db16b231b41c6012c1cf7b1c2c2f8bdcf447924a791b2ce5766f0263e3ce698d`）和 app.js（840488 B，SHA256 `7886640de4fc2cef911fe92f1851b06b07dac1c120ee850492670d09fac0505e`）。OpenAPI 与已知 `c30a8a956715b6ea809db4b87c0f4fcddf8f61de` 相同；线上 `validArticle`、`createArticleVerificationStore`、`bindArticleVerification` 与该源编译结果逐字节一致。不据此声称已证明生产精确 Git SHA，没有读取真实业务记录。

正式接口为 `PUT /api/v1/articles/{id}`，原始 `version` 必填，`verify_items` 为整个对象数组；无独立清单端点。省略文章其他字段时服务端保留旧值，但仍重新校验旧文章。成功返回完整文章及 version+1；旧版本返回409。登录会话逐请求核对 Cookie、精确 Origin 和 CSRF；Token 需 write 与文章所属账号范围；公开模式需显式标头及 Origin，受原公开限流和16KiB正文限制。桌面继续使用原登录/公开协议与每次写入前的 scope 核对，不新增或改变凭证。

同 actor、同幂等键、相同方法/路径/稳定JSON返回原成功响应，不再次修改版本；同键不同请求409。幂等重放重新验证当前 actor/write/CSRF 后返回历史响应，在当前文章账号授权之前，不是新的账号范围检查；每次客户端 scope 核对保留，服务端原子 expected-scope 缺口仍存在。没有文章精确保存收据查询接口；GET 当前内容相同、版本更高不能证明本次请求提交，Unknown 不因相似现状自动确认。

六类流水线 JSON 合计64KiB、每字段12层/4096值节点；未知合法子键保留，危险键拒绝。done缺失、null或非布尔值仍为未知，只有明确的false才是待处理、明确true才是已处理；null清单未知，空数组与之不同。

## 本轮实现

- 清单进入现有文章编辑页，与标题、正文和流水线修改合并到同一 original、草稿key、原始version及完整PUT请求。没有旁路部分保存或选择即发请求。
- 虚拟化条目列表、当前状态、完整只读JSON详情；只能显式修改已有项done，不新增、删除、重排或修改来源/备注等metadata。未知原值不自动归一。
- 撤销仅恢复所选条目打开当前页面时的done值或缺字段，不丢掉此前已经保存的草稿选择。浏览和选择条目不改稿，实际变更才触发原有加密草稿保存；导出包含当前完整清单。
- 共享纯逻辑同时供真实UI和隔离Worker契约使用；最终builder比较同长度、同索引metadata，仅接纳done布尔差异，缺字段旧稿回退原件；继续执行整篇文章结构、总量、真实日期及版本校验。坏旧记录保留只读，不猜测修复。
- 仅从未尝试的排队请求可按原机制替换并保留历史；已尝试、Unknown、冲突及备份恢复请求继续原围栏。新草稿保留，不换键覆盖旧未知请求、不自动重试。工作区仍读取Schema1/2；此类草稿须用0.9.0或后续兼容版本继续编辑，旧候选不会采纳清单改动。
