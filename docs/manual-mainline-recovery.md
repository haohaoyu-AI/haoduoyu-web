# 人工上传生产线恢复

本轮范围为人工上传→配图排版→头条/知乎私人草稿。自动写文仍按当前 `text_saved` 规则保存文字稿。百家号仍未接通。

## 用户页面

配图发布页同时读取最近五篇和独立分页的未完成任务，显示待处理总数；旧任务不会被新稿挤出，后续页明确提供加载入口。页面刷新会重新读取已加载的各页。

正常操作只需一次“求助小鱼”。通知发送中或回调已接受后，页面显示等待接手并自动更新处理进度，不再展示“继续处理”或要求再次点击；Word 已就绪、头条完成而知乎待处理时也展示阶段进度。故障恢复使用“重试求助”，仅在新记录的处理问题或通知结果不明/发送占用已过期且没有活跃执行者时出现。旧失败任务重新通知后先等待，不因保留的旧错误立即再提示重试。

每次明确请求仍使用独立持久事件编号，接收方可以区分新的唤醒；文章编号和原子认领防止重复处理。并发通知受到单一发送占用限制。通知接受只表示 HTTP 回调接受，不表示小鱼已经执行或平台已保存。中断/超时的通知保留 unknown，可核对后恢复，不能据此重传平台文件。`recovery.can_notify` 是服务端是否允许再次通知的技术权限；页面只依据首次未通知状态、`can_retry` 与 `waiting_for_executor` 展示动作和等待，不把允许重试理解成正常流程必须再点。

存在有效执行租约时显示北京时间到期时间，不会强制清锁。实际执行已经结束而租约未到期的任务，沿用 `preview_article_claim_recovery` 与 `recover_article_claim` 的精确快照和原执行结束确认；不能把一般通知当作提前接管许可。

## 执行者

- 先读取原文、现有 Word 输出和每个平台上传记录，再认领。已保存 Word 直接复用；某平台成功后只继续另一平台，不重做已有成稿或重投已保存草稿。
- `renew_article_claim` 用当前活 token 续期；平台为 toutiao 时对应主任务，为 zhihu 时对应独立平台。它不恢复过期凭据，不清围栏、不变状态、不授予浏览器上传。现有六小时租约保留，兼容尚未采用心跳的执行者。
- Word 完成后交给其他执行者，继续使用现有 `release_article_word_claim`，由下一位正常认领。不得复制 token 到文件或报告。
- 若未完成 Word 的声明或已接受分块确实错误/丢失，`restart_article_output` 使用当前活 claim、精确旧 output ID/SHA、新文件声明和结构化原因，原子分配新 output ID 并轮换 token。旧块和旧声明保留在审计中，原文、图片清单、来源不变；旧执行者的分块和 finalize 不能写入新尝试。
- 重做只允许 processing/failed 且没有最终 Word、平台投递记录、上传尝试、草稿链接或读回的阶段。平台结果不明不能用此工具清除。修正 Word 仍必须通过原文、图片和文件哈希核验。
- `read_article_output` 显示已保存输出身份和重做摘要，可用于识别响应丢失后的既有结果；不返回 token。

## 可控与难控

本轮代码改善通知、卡单可见性、Word 修复及认领观测。平台登录、网页导入、漏图、封面和独立回读仍依赖浏览器执行环境；任务库不能证明浏览器已停止，也不能替代真实草稿验收。现有 `article-upload-sop.md`、一次许可及已授权人工重导协议继续适用。

不会增加付费模型重试、改历史回执或自动执行历史积压。通知是按用户操作触发的，持久记录并非已部署的无人值守调度器。
