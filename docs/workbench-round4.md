# 第四轮工作台：部署与运维交接

基线：`4aefa`，分支：`opt/workbench-ui-round4`。本轮补充工作台界面、多条碎碎念、工作提醒、账号公开主页和增量同步接口。本文只记录发布操作顺序与接入边界；未执行远程 DDL、初始化、清库、部署或创建 PR。迁移验证使用一次性本地合成 D1。

## 迁移与发布顺序

本轮只有新增迁移 [`0008_workbench_updates.sql`](../drizzle/0008_workbench_updates.sql)：从 **8 条迁移、19 张表**升级为 **9 条迁移、22 张表**。仅新增以下三张表及其索引、约束，不修改、搬移或重建原 19 张表。

| 新表 | 用途 |
| --- | --- |
| `matrix_note_entries` | 按归属用户、独立 UUID 保存生活及工作碎碎念，包括版本和软删除记录。 |
| `matrix_work_reminders` | 按归属用户、日期及 `source_key` 保存工作提醒摘要，包括版本和软删除记录。 |
| `matrix_account_profiles` | 关联既有账号与规范化公开主页、平台身份；不扩充旧账号行的列。 |

公开主页仅做本地校验和身份识别，不登录平台、不抓取外链，也不取得后台阅读量、收益等非公开统计。

发布端按既有授权发布通道执行：

1. 确认目标库对应本基线，`0000` 至 `0007` 已应用。先取得完整 v8 备份和独立源库 inventory，核验摘要、表清单及行数据，并完成空隔离库恢复验证。按登录用户筛选过的 HTTP 备份不能代替全库 inventory。
2. 只应用 `0008_workbench_updates` 一次。不要重跑初始化、旧迁移或本地 fixture 工具，不执行数据库重置。
3. 核对新增三表、原 19 表 DDL 和既有行数据，再部署对应的新 Worker。运行时绑定、凭据、源站和既有权限配置沿用现状。
4. 发布后用已授权身份核对记录读回、保存收据、账号主页与完整快照；实际发布提交、CI 终态、包摘要及截图证据另行交付，不在本文预填。

[`tests/workbench-backup.test.mjs`](../tests/workbench-backup.test.mjs) 覆盖旧 19 表 DDL、行数据及 inventory 在新增迁移前后保持一致，并核对 0008 元数据快照衔接。该证据不代表已在生产执行迁移。

## 备份、恢复与回滚

完整导出升级为 `haoduoyu-matrix-d1-v9`，在 v8 原有列清单之外加入 `note_entries`、`work_reminders`、`account_profiles`，保留正文、摘要、主页链接、版本、变更号及删除墓碑。用户范围导出会限制私有碎碎念和提醒归属；操作者全库导出与独立 inventory 才用于完整迁移核验。

恢复仅供操作者显式调用，目标必须是已迁移的空隔离数据库；没有 HTTP 覆盖恢复。v1–v8 仍可恢复，缺少的新表数据默认为空。任一新旧业务表非空都会在写入前拒绝恢复；新记录还会验证归属、重复身份、日期时间、版本、变更号、容量和主页规范化一致性。恢复后变更游标高于源修订号；旧会话和登录限流窗口不恢复。

回滚旧 Worker 时保留新三表和全部内容。旧 Worker 不展示新条目、提醒及主页信息，不能据此判断数据已丢失，也不能用旧版导出代替完整 v9 备份。回滚前保留 v9 导出并验证独立恢复；不要删除非空新表或覆盖现有数据。设置中的「30 天」是恢复提示，超过 30 天的内容归档后仍可恢复，没有自动永久删除任务。

## 父任务接入：提醒与同步

工作提醒沿用 `DAILY_NOTES_OWNER_ID` 归属。归属用户的正常会话可编辑；公开编辑沿用已有公开模式、同源与写入请求头规则。碎碎念、提醒写接口不接受 API key 作为授权，也不因保存主页而取得平台登录能力。

父任务只回填获准公开展示的摘要，不传腾讯令牌或原始私密材料。首次写入生成稳定 UUID，并保存 `date`、`source_key`、`version`、`save_id`；同一日期与来源复用已有 UUID，按最新版本更新，不重复创建。实体 UUID 持续复用；同一次操作重试沿用 `save_id`，内容或版本变化后的新操作使用新的 `save_id`。日期和来源键创建后固定。写入后通过该日期的 GET 列表核对同一 ID、版本与内容哈希；结果不明时先读取该日期列表核对同一ID、版本和哈希；必要时仅重发完全相同版本及save_id的原请求。字段、容量、认证和错误码详见 [`/api-docs`](../public/api-docs.html) 与 [`openapi.json`](../public/openapi.json)。本仓库不自动读取腾讯数据，也不把腾讯令牌放到前端。

同步优先使用新增 `GET /api/v1/workbench-snapshot/index` 和 `GET /api/v1/workbench-snapshot?date=YYYY-MM-DD`。索引与日期载荷均为有完整性预算的当前投影；只接受完整成功结果，遇到预算、权限、解析或一致性错误即停止，不从缺失或失败响应推断删除。

- 用 `scope_id + entity_id` 作为映射键，保存每个实体的 `content_hash`。新实体创建、哈希变化更新、哈希未变跳过，删除墓碑用于归档；不要直接永久删除远端内容。
- `scope_id` 变化时建立新基线，不将权限或归属变化解释为旧范围全部删除。跨请求同步前后复核 manifest；索引与明细不一致时重新读取，确认后再应用。
- 日期载荷包含生活、工作碎碎念的稳定 ID，旧逐日记录和新条目保持独立。待办日期和记录时间采用真实来源字段。
- 备忘录没有业务日期，作为全局实体在每个日期载荷中完整附带；按全局哈希和实体映射读取、处理一次，不为每一天重复新建。完整索引也能发现旧日期的修改和删除，不应只扫描最近几天就断言全量同步完成。

既有 `/snapshot` v1/v2 和旧 Notion 接入保持原合同。新接口不会自动改动旧同步内容、创建 Notion 定时任务或启动腾讯抓取；第 5 项平台补录及第 9、12、13 项的外部数据与调度，由父任务接续。网站模块使用免费能力，不新增收费服务依赖。
