# Android 3.0 unified-shell candidate

The current branch prepares `3.0.0` / `versionCode 4`, package `xyz.haoduoyu.personal`, minSdk 26. `MainActivity` opens the shared website at `https://haoduoyu.xyz/?page=todos`. This is an unsigned candidate, not a delivered formal upgrade. Website readiness, physical-device acceptance and signing on the original authorized machine remain release gates. Cloud work does not deploy the website or use the original signing key.

## Current behavior

The existing first-party WebView profile retains cookies, DOM Storage, IndexedDB and standard Service Worker settings. There is no separate native business editor, new native outbox, unrestricted JavaScript interface or native API cache. Existing back handling, file selection, external links, TLS rejection, insets and keyboard handling remain in the shell. Native network events are fixed wake-ups; legacy events carry only bounded counts and a consent-needed boolean, with native origin and JavaScript top-document/origin guards.

The old `OfflineActivity` component name remains resolvable for restored tasks. It never starts `OfflineRuntime` or the old editable native workspace. A restore without a draft opens the shared shell. A restore containing the `draft` key first preserves the exact tab/date/draft values in an independent app-private, read-only recovery file, distinguishing absent keys, null and empty strings. The old SQLite file is not a destination for this record. Verified write, fsync, atomic placement, directory durability and read-back precede finishing the old component. Duplicate content keeps its first recovery timestamp.

If private preservation fails, a read-only recovery screen keeps the text available for copying, complete system-file export and retry. Opening the web from this screen leaves the recovery Activity below it instead of clearing that task entry. A native-only pending boolean adds an explicit shell button/menu action to reorder that recovery page to the front; no draft content is sent to the website or shell Intent. Its saved-instance state retains the draft for recreation. Successful retry clears that pending marker without reloading the existing WebView route. Recovery records are accessible through the existing native read-only recovery entry even without an old database. `recovered_at` describes recovery time, not the original writing time. These records grant no upload consent and enter neither executable queue.

## Old database and consent boundary

The original `haoduoyu-offline.db` name and schema version 1 remain. Raw export reuses the existing chunk/manifest verification and preserves original bytes, including unknown fields, intentionally empty drafts, tombstones, entity versions, operation order, frozen requests, receipt state and conflicts. `haoduoyu-legacy-archive` v1 includes the complete payload, length, SHA256 and provenance. Base64 is an encoding, not encryption.

A verified durable private archive precedes old-engine writes. Only the original SyncEngine owns the old queue, under one process semaphore. It may drain only an already-consented public workspace whose exact origin, account, scope and frozen-wire identity still match an independently verified server target. Private identities, missing consent, changed scope, incompatible requests, corruption or failed backup retain the source and pause recovery. No fallback upload grant or executable import is created.

The native recovery viewer supports local copy and full JSON/text export; large records use file export rather than a large clipboard transaction. Imported archives are separate read-only historical copies. They cannot replace the old database, set consent or initialize either outbox. Corrupt or unsupported old SQLite remains available for explicit local export of its original DB/WAL/SHM/journal files. Old persistent job IDs are cancelled and the old service is disabled; normal 3.0 entry points do not create old native business edits.

## Signing and recovery gates

A formal upgrade must retain the original release certificate `f65c547294ac358bc9c3e3ab8edb3a29d0483182fe01ab74c1fe4e30cbbe0ac5`. The key and password stay on the authorized signing machine; cloud does not copy them or create a replacement formal key.

Keeping the 2.0.1 APK does not make it an in-place rollback from code 4 to code 3. Android uses `versionCode` to block lower-version installation ([official versioning rules](https://developer.android.com/studio/publish/versioning)). Before a formal release, a viable rollback requires a compatible build with the original certificate and a version code higher than the installed version, or a separately verified restoration procedure. The original APK is a preserved reference. Uninstalling or clearing application data is not a rollback procedure and would risk the retained local records. This branch does not build or sign a rollback APK.

Cloud integration must extract only the reviewed `android/` changes and separately review `.github/workflows/android-personal-check.yml`; do not merge this branch's old web tree over current web/backend/data sources. The historical shutdown proposal remains available at [76ba1e3](https://github.com/haohaoyu-AI/haoduoyu-web/blob/76ba1e3ba80dc9a7d1a14a6d138034247b6befa5/android/UNIFIED-V3.md), rather than being presented as current incomplete instructions. The approved Library plan was fully read; failed helper downloads were not successful materialization. Latest explicit consent and release instructions govern the implementation.
