# Read-only data intake checkpoint, 2026-11-09

## What this phase implements

The original shared website interface and its 13 frozen assets remain unchanged. A native “本机数据” menu opens a local JSON backup inspection window. It shows only allowlisted metadata: exact supported format, export timestamp, numeric data revision, identity count, table counts, deletion-marker counts and two SHA-256 values. It does not show usernames, business text, password/token hashes, audit details or stored request responses.

This is a **read-only structural preview**, not an import, restore, synchronization or full semantic validation. `CanImport` is always false. There is no database adapter, restore function, arbitrary JS bridge, source JSON injection into WebView, network upload, source-file write, data reset or profile migration. Existing close/flush/resume code is unchanged.

The file is selected through a native picker with recent-item addition disabled. The inspection code rejects UNC/device/URL paths before filesystem probes, rejects mapped network/unknown drive types on Windows, rejects alternate-data-stream paths, validates reparse/link boundaries and reads a bounded handle with `FileAccess.Read` and `FileShare.Read`. It never accepts a path from the website. This is an application boundary, not a claim that the OS/file-picker or a local cloud-sync service performs no networking or leaves no traces. Managed JSON/string copies can remain until garbage collection; clearing byte buffers is not secure memory erasure.

## Supported contract and limits

- Only exact `haoduoyu-matrix-d1-v9` is supported initially, pinned to `src/backup.mjs`, `src/security.mjs` and article pipeline columns at commit `3c0af618f2c897ba078c7ab1b06df213e6ad0ca1`. Older/newer formats, CSV and old native databases fail closed. This pin does not establish the currently deployed exporter version or a particular user's export provenance.
- The complete 19-table/column allowlist must match. Checks include strict UTF-8, duplicate/dangerous JSON keys, safe integer values, exact field presence, primitive row shapes, primary/composite identity uniqueness and basic owner/account/article/group/template references.
- Input is bounded at 20 MiB, depth 16, 100,000 total rows and 262,144 UTF-16 units per string. The accepted numeric subset uses integer JSON spellings within JavaScript safe-integer bounds; decimal/exponent spellings are deliberately unsupported. These are preview limits, not a promise that all valid server backups fit them.
- The raw-file hash is separate from the embedded checksum of UTF-8 `JSON.stringify(stable(data))`. Arrays retain order. Ordinal key ordering and explicit JSON string escaping match the accepted exact-key/integer subset. Synthetic fixtures are generated by the pinned JavaScript `stable()` algorithm and checked in C#.
- Users, API keys, audit and idempotency tables are counted but excluded from any future business import plan. Their contents never leave the inspection component. No prior session, credential, receipt, queue or upload permission is revived.

## Provenance and completeness are unverified

A matching checksum can be created by anyone who can rewrite a file. It is not a signature, producer identity or authorization. `source_revision` is a database change cursor, not a software version or Git commit. The v9 envelope does not declare export ownership scope or coverage. The existing server exporter can scope private tables while retaining other tables, so empty private tables do not prove missing source data and an accepted file is not called “your complete backup.” Multiple identities are reported and never silently remapped.

The checker deliberately does not validate every business enum, timestamp, date, version rule or rich JSON-text field. For example, a structurally valid but semantically invalid completion/version value can still produce an aggregate preview. The UI says “结构检查” and “基本关联”; it never calls the records safe to import. Duplicate/conflict comparison with current desktop records has not run because the preview does not read that database.

## Verification and pending gates

Linux synthetic checks cover cross-runtime canonical checksums, all 19 table shapes, Unicode/control escapes, raw/payload hash distinction, tombstone counts, metadata-only output, bad formats/checksums/types/keys/references, duplicate identities, row/depth/string/byte limits, cancellation, repeated reads and unchanged input/sentinel bytes. Static checks assert no write/database/network/bridge path and early source-path restrictions. Windows x64 cross-compilation checks native UI/test code, not Windows interaction.

The prepared Windows harness inspects only the synthetic fixture, shows/closes the native metadata window twice, scans its formatted text for synthetic private markers and captures its actual HWND. It does not automate the native file-picker, read real user files or prove Windows drive/reparse behavior. No new Windows CI run has been performed for this checkpoint yet. Those results must be checked for the final committed source before claiming UI acceptance.

## What is required before real data import

1. Resolve the actual authorized source/export, producer version, ownership scope and coverage. Do not ask the user to upload a credential-bearing full backup to chat or GitHub. Prefer an authorized business-only export prepared without copying credentials, private sessions, audit contents or old request capabilities.
2. Implement and test the exact source-to-local schema mapping, owner isolation, labels/relationships/tombstones and full business validation. Reject unsupported fields rather than silently dropping them. Never infer a current schema from the numeric data revision.
3. Read-only comparison must identify exact duplicates, conflicts and records unsupported by the desktop candidate. The source and existing local data remain authoritative and unchanged.
4. Create and verify a recoverable backup, stage the proposed import separately, then require the appropriate explicit source/target/write authorization. Atomic application, interruption rollback, repeat-import idempotency and independent reopen/count/content verification must pass on synthetic copies before real writes.
5. Formal release still requires validated data import/export/restore, installer and upgrade retention, signing/trust behavior, supported business routes and actual Windows acceptance. This checkpoint is not a finished official release.
