## Normal owner-scoped maintenance interface

The existing authenticated `/mcp` article-data dispatch exposes:

1. `preview_site_data_backfill(scope)`: one page of at most 25 candidates; returns count and opaque fingerprint, not source bodies, credentials or draft payloads.
2. `apply_site_data_backfill(scope, request_key, snapshot_fingerprint)`: explicit maintenance in one D1 batch. It rechecks the exact ordered page inside the transaction, copies only those metadata rows and stores an immutable receipt in the existing owner/request-key namespace.
3. `read_site_data_backfill_receipt(request_key)`: independent read after a response is lost. A known committed request can be retried with identical arguments; changed scope/fingerprint is refused.

Scopes are `article_history`, `topic_fences` and `topic_control_keys`. Each next page requires a fresh preview and request key. A batch receipt proves that page, not completion of every page. Interrupted transactions roll back copies and receipt together. A committed but lost response is recovered from the original receipt. Other owners cannot read or apply that snapshot. Source records are retained; old conflicts are copied with no selected winner.

Do not run history backfill to countermand the user's latest request to clear website records. Production maintenance requires its actual intended scope and normal authorization. No maintenance was run in production in this task.
