# Free account response diagnostics

Base: production v110, `80715ec1706168c6d7d12907f066c3d9a23f05e2`. This change is independent of the unpublished account-save UI patch.

The existing accepted owner refresh still makes one anonymous, manual-redirect request per public account. Responses passing the existing public-access check are queued in memory. The primary scan result is committed before any diagnostic R2 operation. A single 200ms optional waiting budget covers cleanup, capture and diagnostic metadata persistence; timeout returns the already durable primary result. Diagnostic I/O never serializes source requests or consumes the primary commit lease. The sample is a **derived**, possibly **truncated** allowlist DOM plus SHA-256/byte count of the original decoded response string, not original HTML, a browser render, a real DOM fixture or metric verification. `can_verify_metrics` is always false; original candidate parsing and thresholds receive the original response unchanged.

The sample retains supported article/profile links, title text, date attributes, author markers, and literal displayed metrics such as `12万阅读`. It omits scripts, styles, forms, inputs, hidden subtrees, credential-related attributes, arbitrary URLs, long opaque text, and private-field assignments. Redaction removes the smallest subtree containing a credential assignment, including quoted JSON or keys/values split across inline elements; sensitive class/name/id labels also suppress their contents. A conservative storage-only login/challenge marker check refuses samples with `reason: restricted_response` without changing candidate parsing. Plain JavaScript fallback notices can set `js_hint`; this is a hint, not proof that browser execution is necessary. Closed native details/dialog bodies are omitted; external CSS and rendering are not evaluated. This intentionally lossy diagnostic can omit useful content and must never be reparsed to qualify articles. Public `/c/user/token/…/` profile identifiers are allowed only through the existing canonical account URL validator, not treated as login credentials.

R2 JSON is limited to 64 KiB total, including metadata; the DOM budget accounts for JSON escaping and UTF-8. Original raw HTML, response/request headers, cookies, and secret script payloads are not stored. R2 keys use a hashed owner namespace, exact scan/account IDs, and a versioned prefix. Existing scan snapshots define account membership. No table, migration, background collector, arbitrary URL proxy, browser automation, credential access, model call, draft write, or deployment is added.

Authenticated `GET /api/imitation/discovery/diagnostic?scan_id=<uuid>&account_id=<uuid>` returns JSON with private/no-store headers. Only these two exact parameters are accepted. Wrong owner/account returns 404, malformed IDs return 400, and expiration or an older-than-latest-two scan returns 410 before R2 reads. Scope is rechecked after delayed reads/writes, using the current time after the last database await. Budgeted production captures additionally require a persisted completed summary with the same account and source hash, so an unacknowledged timed-out object cannot be read. Unknown stored properties are not returned. Storage errors return a fixed 503 message. This is an owner review endpoint, not a public HTML viewer.

Retention is **logical denial at 24 hours from scan creation**, and **physical lazy cleanup on the next accepted normal refresh**. Without a new refresh, an object may remain physically stored but cannot be read through this endpoint. Cleanup re-reads the newest scans after R2 list completes; cancellation stops subsequent cleanup/capture operations. It only deletes correctly named, version-marked objects in this owner's diagnostic namespace that are expired or outside the newest two accepted scans, never article objects or other owners' resources. Native R2 I/O already started cannot be canceled: a late put checks cancellation/scope and attempts deletion of its exact own key; incomplete production objects remain unreadable if that deletion fails. Listing is bounded at 1,000 objects; truncated cleanup disables capture until later refreshes clear the backlog. R2 custom metadata inclusion follows the [official Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/); the pinned Workers types omit that documented list option.

All new tests use synthetic HTML, an isolated in-memory SQLite database, and an R2 map. No captured live response exists yet. Production's earlier HTTP 200 / zero-card / unverifiable scans retained hashes only; their DOM cannot be reconstructed. After root review and deployment, the next normal user refresh is required for genuine evidence and subsequent parser work. Nothing here establishes current account follower counts or successful live collection.

Validation: both diagnostic suites and all `tests/hot-article-*.mjs`, TypeScript, lint for changed files, and production build. Review cases cover stuck list/put, a 61s clock jump, quoted/split credentials and semantic labels, TTL crossed during final DB awaits, a new scan during delayed list, and canceled cleanup. No push or deployment.
